# Bug Register

This register tracks verified defects and their remediation. Application source and tests establish implemented behavior; proposed fixes are not acceptance evidence. Preserve billing and user data, and update [TASK](docs/08-delivery/TASK.md) when a defect affects a delivery task.

## BUG-001 — Provider retry delay longer than one day is dropped

- **Status:** IN_PROGRESS — partial mitigation only. **Priority:** P1. **Related task:** T-041 (rate handling), T-071 (retry UX).
- **Evidence at `9014f0d`:** `generateStudioScene` given a synthetic HTTP 429 and `Retry-After: 86400` returns 86400, but `86401` and `100000` return `retryAfterSeconds: null`. At that revision, unit tests explicitly asserted the 86401 behavior. At that revision, the gateway and client also bounded the value at 86400; the generation-job schema rejected larger values. In `enforceRetryDelay`, an absent value means no persisted minimum wait is enforced. This can allow a separately authorized new local attempt before the provider's stated minimum; no automatic retry was observed or claimed.
- **Reproduction:** Call `generateStudioScene` with a synthetic transport returning a 429 `Response` and the two `Retry-After` header values. Inspect the returned sanitized metadata; use no provider key or real network call. The exact 86400/86401 boundary is sufficient to show the loss.
- **Earlier partial mitigation:** The gateway retained the durable active marker for a 429 with a present invalid or unsupported delay, blocking new server attempts across restart until explicit external review. At that stage the original delay was not persisted or enforced after acknowledgement. Missing `Retry-After` retains its prior behavior.
- **Earlier server-journal foundation:** Delays of 1–86400 seconds became durably enforced by the gateway after restart and acknowledgement, including requests from another client sharing the journal.
- **Extended delay implementation:** Supported seconds and HTTP-date delays through 2147483647 seconds now flow through the gateway and local job state. Values outside that range or malformed present headers remain in the explicit external-review path. A synthetic desktop Chromium ZIP round-trip preserved a long delay and imported-review markers; physical-device backup, comprehensive browser concurrency, real-provider and independent security evidence remain open; the defect is not yet closed.
- **Synthetic Chromium cross-tab evidence:** Two tabs sharing one isolated origin created two synthetic products and prepared attempts. After one recorded a definitive provider-limit failure with 86401 seconds, the other tab reloaded and could not mark its prepared attempt submitted. Advancing its test clock to the recorded deadline allowed the local state transition; no provider call was made. This is not installed-device, real-provider or independent security acceptance.
- **Synthetic gateway and UI evidence:** A built desktop Chromium app used an isolated loopback gateway with a synthetic credential, image, mask and transport returning HTTP 429 with `Retry-After: 86401`. The UI displayed the full wait, and the format 3 journal recorded a definitive failure and retry deadline. After reload, history retained the delay; preparing and authorizing a retry before expiry produced a local wait message. The browser network trace showed one generation request and no second generation request. This does not independently test a direct client, an actual provider or elapsed-time retry.
- **Malformed date hardening:** The adapter now requires a parsed HTTP date to round-trip exactly, rejecting impossible dates and mismatched weekdays instead of allowing JavaScript to normalize them. Present malformed guidance uses the existing durable external-review gate. Synthetic regression tests cover adapter classification and gateway blocking after restart; this does not remove the other open acceptance requirements.
- **HTTP-date clock-skew mitigation:** A synthetic 429 demonstrated that a local clock two hours ahead turned a future one-hour provider interval into zero. For HTTP-date guidance the adapter now requires a valid provider `Date`, takes the longer of provider-relative and local-clock intervals, and routes absent or invalid provider dates to manual review. A gateway test verifies the resulting wait survives restart. Later clock changes and inaccurate upstream dates remain limitations; no real-provider or security acceptance is implied.
- **Confirmed forward-clock bypass:** A synthetic gateway received `Retry-After: 86401`, recorded and acknowledged the definitive failure, then restarted after its injected wall clock advanced by 86401 seconds without the corresponding real wait. A separately approved new attempt reached the synthetic transport (two total calls). Absolute deadline checks therefore cannot prove elapsed time after a clock jump or restart. No real provider was contacted.
- **New gateway waits:** Newly recorded bounded provider waits use format 4 and the monotonic elapsed-proof path. A synthetic gateway test shows a forward wall-clock jump and restart do not release such a wait early. Older format 3 waits now require separate external review before a new dispatch; this remains a human attestation rather than elapsed-time proof.
- **Separate-process evidence:** Synthetic monotonic-clock tests ran two Node processes against one journal. Both were blocked just before the interval; concurrent later reservations shared the durable proof. Killing one process before proof publication caused a restarted process to wait a full new interval. This does not establish sleep, fsync-failure or real-provider behavior.
- **Real elapsed-time evidence:** A synthetic gateway test used the normal process monotonic clock with a two-second provider delay. After gateway instance restart and an injected forward wall-clock jump, an early separately approved attempt was blocked with no second transport call; after a real 2.2-second wait, another separately approved attempt reached the fake transport. The complete gateway test file passed 52 tests. The gateway instances ran in one OS process and the wall clock and provider were synthetic.
- **Proof publication faults:** Synthetic file-sync, link and directory-sync failures prevented the locked dispatch; after filesystem operations recovered, a separate invocation completed the proof and dispatched. This is injected I/O failure evidence, not a physical power-loss test.
- **Crash during proof publication:** A synthetic child was killed after linking the proof but before directory sync. Its stale journal lock blocked reopening and no next reservation appeared. After controlled removal of the lock in the disposable test directory, reopening synchronized the directory and accepted the retained proof. This is not a production recovery procedure or physical power-loss test.
- **Format 4 browser evidence:** An isolated desktop Chromium UI used a synthetic loopback gateway returning `Retry-After: 86401`. The UI displayed and retained the delay across reload; a separately prepared and authorized retry before expiry was blocked locally, while the fake transport recorded one call total. The gateway journal recorded format 4 with the full duration. This does not prove actual elapsed-time or real-provider behavior.
- **Required fix:** Preserve and enforce valid representable provider delays across provider adapter, gateway, API, persisted job/attempt state, new-job and same-job retry paths. Values outside the supported representable range or invalid/ambiguous guidance must not silently become a shorter wait: define a fail-closed, reviewable recovery. Do not truncate a provider's explicit minimum or auto-resend. Preserve known 429 classification and UNKNOWN billing semantics where outcomes are actually ambiguous.
- **Acceptance:** Synthetic end-to-end tests cover seconds and HTTP-date forms at the existing boundary, larger values, invalid/overflow inputs, missing headers, restart and concurrent tabs, same-job retry and new job, backup/export/import and old-client/schema compatibility. Prove no provider call before a valid explicit minimum expires, including forward wall-clock jumps and process restart, and separately authorized retry afterward. Document cross-profile/direct-client limits and any required version/migration; perform appropriate security review. Test without real keys or paid requests.
- **Open design:** Select safe bounds and a durable explicit manual-review state for unrepresentable values, including its authorization and recovery semantics. Do not silently alter existing data or let imported histories bypass their trust barriers. This defect is not resolved by this record.

## BUG-005 — Failed service-worker installs consume shell-cache slots

- **Status:** VERIFIED for the scoped fix. **Priority:** P2. **Related task:** T-011.
- **Reproduction:** In a simulated worker with an existing active shell, repeated new-build `addAll` failures left newly opened empty caches. After seven failures the configured eight-shell limit prevented another install, even though the failed builds had never installed.
- **Fix and evidence:** Under the cooperative Web Lock, a failed `addAll` now attempts to remove only the cache newly opened by that install; pre-existing shell caches are retained. The regression covers repeated failures, an existing cache, a later successful install and the no-lock conservative path. In isolated Chromium, a synthetic server returned 404 for a required icon; the built worker went from `installing` to `redundant` and no shell cache remained. Nine worker tests and the production build passed.
- **Active-update observation:** With an active built worker and two isolated Chromium tabs, a synthetic newer worker ID and a 404 for a required icon caused the new worker to become redundant. The original worker and cache remained, both tabs displayed the update failure, and an unsaved synthetic SKU remained in the editor. Once the server returned the icon, the same newer worker installed and waited for user action; both caches and the draft remained. The newer worker was a modified copy of the same build, not a separately built application.
- **Limits:** Cache deletion is best effort; if deletion fails or Web Locks are unavailable, a failed cache may remain and require the existing recovery path. These browser observations do not establish natural quota exhaustion, all multi-tab races, genuinely different application builds or physical-device behavior. Revert the worker and tests together if necessary; preserve user data and existing shell caches.
